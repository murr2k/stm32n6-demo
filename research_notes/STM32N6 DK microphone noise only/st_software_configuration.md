## Objective: exact microphone configuration in every ST package that records from U13 (comparison)

### Takeaway
Six ST code bases touch the DK microphone: the BSP audio driver, the `MDF_AudioRecorder` example, the GS-Audio package (two clock variants on a patched BSP), the `VENC_RTSP_Server` application (a forked "multi" BSP), the CubeMX `Templates_Board` stub, and X-CUBE-AUDIO-KIT (not available locally). They agree on Sinc4 + reshape filter (decimate by 4) + HPF at 0.000625 x Fpcm, PE2/PE8 as AF4 push-pull, no pull, very high speed, DiscardSamples = 0 and no start-up delay, but they differ in gain (SCALE +6 dB to +42 dB), in how 24-bit data becomes 16-bit (keep the low 16 bits with saturation vs transfer the 16 MSBs), in clock source (HSE vs HSI vs MSI), in serial mode (NORMAL_SPI vs LF_MASTER), in bitstream edge (FALLING everywhere except the VENC channel 0 default and the template stub, which are RISING), and in whether the DMA buffer and DMA node are placed in non-cacheable memory (every application does it, the stock BSP does not). There is no audio-record test in `Examples/BSP` of STM32CubeN6 for this board.

### Cited Findings

#### Which packages exist and which do not
- The BSP declares two input instances, "Instance 0 is SAI path / Instance 1 is MDF path", and two devices: `AUDIO_IN_DEVICE_ANALOG_MIC 0x01U` ("Analog microphone input from 3.5 audio jack connector") and `AUDIO_IN_DEVICE_DIGITAL_MIC 0x10U` ("MP23DB01HPTR digital microphone") - [BSP stm32n6570_discovery_audio.h L182-195](https://github.com/STMicroelectronics/stm32n6570-dk-bsp/blob/v1.3.0/stm32n6570_discovery_audio.h#L182-L195)
- `Projects/STM32N6570-DK/Examples/BSP` contains only touchscreen, LCD, SD and camera demos (`BSP_examples[]` = `Touchscreen_demo1..3`, `Lcd_Demo`, `SD_Demo`, `Camera_Demo`, main.c L46-55; sources are `camera.c`, `lcd.c`, `sd.c`, `touchscreen.c`). No file in that example calls `BSP_AUDIO_IN_*`; the only audio-related matches are `DEFAULT_AUDIO_IN_BUFFER_SIZE` in its conf header and `HAL_MDF_MODULE_ENABLED` - [CubeN6 Projects/STM32N6570-DK/Examples/BSP/FSBL/Src/main.c](https://github.com/STMicroelectronics/STM32CubeN6/blob/main/Projects/STM32N6570-DK/Examples/BSP/FSBL/Src/main.c)
- In the whole `Projects/STM32N6570-DK` tree only three projects contain microphone code (grep for `BSP_AUDIO_IN_`, `HAL_MDF_AcqStart`, `MDF1_Filter0` in .c files): `Examples/MDF/MDF_AudioRecorder`, `Applications/VENC/VENC_RTSP_Server`, and `Templates_Board` (init stub only) - [CubeN6 Projects/STM32N6570-DK](https://github.com/STMicroelectronics/STM32CubeN6/tree/main/Projects/STM32N6570-DK)
- GS-Audio does not compile the stock BSP audio driver; its Makefile takes `../../Projects/Common/Patch/stm32n6570_discovery_audio.c` (Makefile L18-19) plus one of two override files: `stm32n6570_discovery_audio.patch.hsi_600_400.c` for the `bm` and `freertos` builds (bm.mk L2, freertos.mk L4) or `stm32n6570_discovery_audio.patch.msi_4_4.c` for `bm_lp` and `freertos_lp` (bm_lp.mk L3-4, freertos_lp.mk L3) - [GS-Audio Projects/GS/Makefile](https://github.com/STMicroelectronics/STM32N6-GettingStarted-Audio/blob/v2.3.0/Projects/GS/Makefile), [bm.mk](https://github.com/STMicroelectronics/STM32N6-GettingStarted-Audio/blob/v2.3.0/Projects/GS/bm.mk), [bm_lp.mk](https://github.com/STMicroelectronics/STM32N6-GettingStarted-Audio/blob/v2.3.0/Projects/GS/bm_lp.mk)
- X-CUBE-AUDIO-KIT is a further ST package that supports the STM32N6570-DK and optionally the STEVAL-MIC008A; an ST employee named it as the place to find "example settings for this microphone". Its sources were not available locally and its wiki could not be fetched - [st.com X-CUBE-AUDIO-KIT product page (search snippet)](https://www.st.com/en/embedded-software/x-cube-audio-kit.html), [ST community thread 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)
- No package named "x-cube-n6-ai-voice" was found by web search; the audio AI package for this board is STM32N6-GettingStarted-Audio (audio event detection and speech enhancement in one repository) - [GS-Audio README](https://github.com/STMicroelectronics/STM32N6-GettingStarted-Audio/blob/v2.3.0/README.md)

#### MDF_AudioRecorder details

### Inferences
- Derived frequencies, stock BSP, assuming HSE = 48.000 MHz exactly: kernel 48/6 x 172 / 28 = 49.142857 MHz for 8/16/32/48 kHz. 8K, 16K, 32K: proc 24.571429 MHz, PDM clock 24.571429 / 12 = 2.047619 MHz, giving 7998.5 Hz (/256), 15997.0 Hz (/128), 31994.0 Hz (/64). 48K: PDM clock 24.571429 / 8 = 3.071429 MHz, 47991.1 Hz (/64). 96K: kernel 688 / 7 = 98.285714 MHz, proc 49.142857 MHz, PDM clock /16 = 3.071429 MHz, 95982.1 Hz (/32). 11K, 22K, 44K: kernel 192 / 17 = 11.294118 MHz, proc /1, PDM clock /4 = 2.823529 MHz, giving 11029.4, 22058.8, 44117.6 Hz. All rates are 0.02 % to 0.26 % off nominal by construction.
- MDF_AudioRecorder, GS-Audio (HSI builds) and VENC_RTSP_Server run the same dividers from HSI (64 MHz / 8 x 172 / 28), so the nominal PDM clock is again 2.047619 MHz but with HSI tolerance instead of crystal accuracy. The README's "49.152MHz / 24,576MHz / 2.048MHz" are rounded-up nominal values; the .ioc itself says 49142857.14 Hz.
- GS-Audio low-power builds: 4 MHz MSI / 1 / 7 = 571.43 kHz PDM clock, total decimation 9 x 4 = 36, so 15873 Hz (0.79 % below 16 kHz).
- SCALE in dB for the gains used (even codes are exact bit shifts per RM0486): Gain -6 = 0x2A = -18.1 dB, -4 = 0x2C = -12 dB, 2 = +6 dB, 8 = +24.1 dB, 10 = +30.1 dB, 14 = +42.1 dB, 18 = +54.2 dB.
- The Templates_Board MDF block is a CubeMX default stub (output clock disabled, CKI clock source, FastSinc, decimation 2, no RSF, no HPF). It cannot record from U13 as written, because the microphone gets no clock; it is not evidence of an ST-recommended setting.
- The stock BSP is the only ST code path where the MDF DMA destination buffer and the DMA linked-list node sit in ordinary cacheable RAM with no cache maintenance in the callback. Every ST application that actually runs with the D-cache on (MDF_AudioRecorder, GS-Audio, VENC_RTSP_Server) moves both to a non-cacheable section. An application that calls the stock `BSP_AUDIO_IN_Record(1, ...)` with the D-cache enabled can therefore read stale cache contents instead of what the DMA wrote (stale or garbage samples). BSP v1.3.0 fixed the same class of problem for the SAI path only ("Correct SAI_MspInit() to ensure audio output is available when all RAM is non-cacheable"), not for the MDF path.
- The stock BSP enables the MDF1 and GPDMA1 bus clocks without their sleep-enable bits, whereas GS-Audio turns on every low-power clock enable before it sleeps in WFI. A system that idles in WFI (any RTOS) and uses the stock BSP MSP code as a model would stop the MDF and its DMA during sleep.

## What gain does ST use for this microphone in each package and sample rate, what does the documentation say about expected signal level, and is about +40 dB the documented norm?

### Takeaway
There is no documented norm: an ST employee wrote in October 2026 that there is "no official configuration" for the MP23DB01HP on the DK. The HAL `Gain` values in ST code are 14 (+42.1 dB SCALE, MDF_AudioRecorder, with the 16 MSBs kept), 2 / 10 / 18 / -6 / -4 (BSP, by sample rate, with the low 16 bits of the 24-bit result kept and saturated) and 8 (GS-Audio low-power build). The BSP table is exactly the largest SCALE that AN5795's formula allows for a full-scale PDM input with Sinc4 and the reshape filter on, so "+40 dB" is what the stand-alone example uses, not what the BSP uses, and the two differ by 12 dB in net PDM-to-PCM16 gain once the 16-bit conversion is taken into account.

### Inferences
- The BSP table is AN5795's "rule 2" limit evaluated for Sinc4 with the reshape filter on (NB = 22) and a full-scale bitstream (SINpp = 2): D = 32 gives 2^22 / (2 x 2^20) = 2 = +6.02 dB (Gain 2); D = 16 gives 2^22 / 2^17 = +30.1 dB (Gain 10); D = 8 gives 2^22 / 2^13 = +54.2 dB (Gain 18); D = 64 gives 2^22 / 2^25 = -18.06 dB (Gain -6, used for 11 kHz). So the BSP is a "unity, never saturate the reshape filter" setting, not a microphone-level setting. The 8 kHz entry (Gain -4 = -12 dB) is 6 dB above that limit and 6 dB hotter than every other rate.
- Net gain from PDM full scale to 16-bit PCM full scale (G_norm), assuming the 24-bit result is left-aligned in bits 31:8 of the data register (consistent with the HAL reading the 16 MSBs at `DFLTDR + 2`):
  - BSP, GS-Audio HSI builds, VENC (low 16 of 24 bits, saturated): G_norm = 20 log10(D^4 x S / 2^15) = +36.1 dB at 11, 16, 22, 32, 44, 48 and 96 kHz, and +42.1 dB at 8 kHz.
  - MDF_AudioRecorder (16 MSBs of 24): G_norm = 20 log10(2^20 x 2^7 / 2^23) = +24.1 dB.
  - GS-Audio low-power builds: 20 log10(9^4 x 2^4 / 2^15) = +10.1 dB.
- With the datasheet sensitivity this predicts, for a 94 dBSPL 1 kHz tone: BSP at 16 kHz about -4.9 dBFS in the 16-bit stream (clipping at about 99 dBSPL); MDF_AudioRecorder about -16.9 dBFS; GS-Audio low-power (microphone in its low-power mode, -24 dBFS sensitivity) about -13.9 dBFS. Conversational speech at 60 to 70 dBSPL would sit near -39 to -29 dBFS in the BSP stream and -51 to -41 dBFS in the example. The microphone's own noise floor (-41 - 65 = -106 dBFS A-weighted) maps to about -70 dBFS(A) in the BSP stream and -82 dBFS(A) in the example.
- A design that copies "Gain = 14" from the example but converts like the BSP (low 16 bits) would be 36 dB hotter than the BSP and clip at about 63 dBSPL; a design that copies the BSP's "Gain = 2" but keeps the 16 MSBs (MsbOnly or >> 16) would be 12 dB quieter than the example (speech near -63 to -53 dBFS) and would look like "noise only". The gain value cannot be compared across packages without the conversion step.
- In MDF_AudioRecorder the scale output reaches the 22-bit reshape-filter limit when the PDM signal is at -36.1 dBFS (99 dBSPL); louder input saturates inside the filter chain rather than in a visible software clamp.

### Gaps
- No ST document states an expected PCM level for this board, and none states a recommended gain for U13. The only ST statement found is the forum reply that no official configuration exists.
- The meaning and unit of `CTRL_X_CUBE_AI_SENSOR_FS (112.5F)` is not documented in the README; it does not equal the MP23DB01HP AOP (135 or 120 dBSPL).
- The G_norm figures are computed, not measured, and ignore the Sinc4, reshape-filter and HPF frequency responses.

## Which bitstream edge and which serial interface mode does ST use, and is there any comment explaining the choice for U13?

### Takeaway
The BSP, MDF_AudioRecorder and both GS-Audio variants sample `MDF_BITSTREAM0_FALLING`; no source comment or README explains why. The schematic and datasheet explain it: U13's L/R pin is pulled to VDD_MIC, which makes DOUT valid while the clock is high. Serial mode is `MDF_SITF_NORMAL_SPI_MODE` everywhere except the GS-Audio low-power build (`MDF_SITF_LF_MASTER_SPI_MODE`), although AN5795 calls LF_MASTER "highly recommended" for digital microphones. The VENC_RTSP_Server default (one microphone) samples the rising edge on filter 0, the opposite of the BSP.

### Cited Findings

- ST technical moderator Saket_Om (Nov 25, 2025, marked best answer), on two microphones sharing PE8: two MDF instances are required, instance 1 reuses instance 0's serial interface and takes the opposite edge from instance 0; the question quoted the example's on-board setup as "Bitstream Matrix: Falling front" (paraphrased from the fetched page) - [ST community thread 158093](https://community.st.com/stm32-mcus-embedded-software-32/interleave-audio-by-connecting-steval-mic008a-dual-mems-to-stm32n6570-dk-cn5-158093)

### Inferences
- With L/R = VDD the microphone drives DOUT after the rising clock edge (driven within 19 ns, valid within 120 ns) and releases it 4 to 17 ns after the falling edge. At 2.048 MHz the high phase lasts about 244 ns, so the data is stable just before the falling edge: `MDF_BITSTREAM0_FALLING` is the electrically correct choice for U13, and the choice follows from the L/R strap, not from anything stated in the software.
- On the rising edge PE8 has been high impedance for about half a clock period and the pin is configured `GPIO_NOPULL`, so `MDF_BITSTREAM0_RISING` reads whatever charge is left on the line (often the previous bit, but not guaranteed). The VENC_RTSP_Server default therefore looks like it is written for the "other" microphone of a STEVAL-MIC008A pair on channel 0, or it relies on bus hold; it is an ST code path that samples U13 on the edge where U13 is not driving.
- The BSP's NORMAL_SPI choice costs a processing clock 12 times the PDM clock (24.57 MHz for 2.048 MHz) where LF_MASTER would need only 2 times; it keeps clock-absence detection (Threshold = 31 is that detector's time-out), which LF_MASTER does not provide.

### Gaps
- No ST source file, README or wiki page read here explains the edge choice or mentions the L/R strap. The schematic image was read visually for the R106 connection (LR to VDD_MIC); the netlist text confirms R106 = 10K next to U13 pins but not its far end.
- The L/R wiring of the two microphones on the STEVAL-MIC008A was not looked up.

### Inferences
- Computed PDM clocks (HSE = 48 MHz exact): 2.047619 MHz for 8/16/32 kHz, 3.071429 MHz for 48 and 96 kHz, 2.823529 MHz for the 44.1 kHz family. All are between 1.5 and 3.3 MHz, so the stock BSP always runs U13 in performance mode (sensitivity -41 dBFS, AOP 135 dBSPL).

A configuration near 1.0 to 1.1 MHz sits at a mode boundary, which may explain the "silence with bursts" user report; this is a hypothesis, not something ST confirmed.
- The user-measured 2.03393 MHz is 0.67 % below 2.047619 MHz, which is ordinary HSI error and well inside the microphone's range; it does not explain a noise-only capture.

### Gaps
- No ST statement was found on whether U13 may be run in low-power mode on the DK, or on behaviour between 1.1 and 1.5 MHz.
- The datasheet read is Rev 2 (July 2020). An ST employee quoted "a maximum wake-up time of 20 ms from the datasheet", which differs from the 10 ms in Rev 2; the current revision was not read.

### Inferences
- In GS-Audio the "selection" is entirely physical: with nothing in CN5 the firmware hears U13; with a STEVAL-MIC008A in CN5 the same firmware, unchanged, would hear whichever of the two daughterboard microphones drives PE8 during the clock-high phase (it samples the falling edge only and uses one filter).
- The instance number, not the `Device` field, decides between codec (headset microphone, SAI) and MDF (U13). Passing `AUDIO_IN_DEVICE_DIGITAL_MIC` to instance 0 would still record the headset jack, and an empty jack there records noise; this matches a guess made by a community member, but the reporter in that thread said he was using the MDF path.
- The sensor name `"imp34dt05"` in the GS-Audio configuration is a leftover from another board; the package was not re-parameterized for the MP23DB01HP's sensitivity.

### Gaps
- Whether ST validated GS-Audio's audio event detection thresholds (`SILENCE_THR 3000.0F`) against the DK microphone level is not documented.
- No other ST N6 audio AI package (voice, keyword spotting) was found; "x-cube-n6-ai-voice" returned nothing in search, so it either does not exist under that name or is not indexed.

## What does UM3300 say about the microphone (section 7.15.2), connector CN5, solder bridge defaults (SB19 etc.) and any limitation?

### Takeaway
UM3300 Rev 1 gives four sentences on the microphone: U13 is on the bottom side, CN5 takes the STEVAL-MIC008A, only two microphones are supported because CN5 has one data signal, and U14 switches PE8 to the daughterboard automatically. The only microphone-related solder bridge in the manual is SB41 (PE12 as a second data line, OFF by default). SB19 appears only in the schematic, where it joins VDD3V3 to VDD_MIC and is drawn closed. The manual lists no audio or microphone limitation.

### Cited Findings
- Section 7.15: the board has "An audio codec with an SAI interface and a 3.5 mm audio jack connector (for stereo earphones and one analog microphone)" and "A digital MEMS microphone and microphone daughterboard connector". Section 7.15.1: the codec is driven through I2C2 (100 kHz), address 0x34/0x35, interrupt on PB1; "Warning: The SAI signals are multiplexed with trace signals." - [UM3300 Rev 1, sections 7.15 and 7.15.1, p.18](https://www.st.com/resource/en/user_manual/um3300-discovery-kit-with-stm32n657x0-mcu-stmicroelectronics.pdf)
- Section 7.15.2, complete: "A digital MEMS microphone (U13) is ON on the bottom side of the STM32N6570-DK main board. A microphone daughterboard connector (CN5) is implemented close to U13, to support the STEVAL-MIC008A MEMS microphone daughterboard. Only two microphones (left and right channels) on these boards can be supported due to only one data signal on CN5. By default, U13 is connected to the data signal of SAI_PDM on the STM32N657X0H3Q microcontroller. When a microphone daughterboard is plugged into CN5, the data signal is switched to the microphone daughterboard automatically (through U14). Note that a second reserved data pin (PE12) in CN5 pin5 is multiplexed with the ARDUINO connector." - [UM3300 Rev 1, section 7.15.2, p.18](https://www.st.com/resource/en/user_manual/um3300-discovery-kit-with-stm32n657x0-mcu-stmicroelectronics.pdf)
- Section 8.5, Table 14 (CN5 pinout): pin 1 GND, 2 VDD_MIC (3.3 V), 3 NC, 4 "PDM clock (CK-PE2)", 5 "PDM data reserved (PE12)(1)", 6 "PDM data (D1-PE8)", 7 to 9 NC, 10 "Microphone board detection", 11 NC, 12 VDD_MIC (3.3 V), 13 to 18 NC, 19 VDD_MIC (3.3 V), 20 GND. Footnote: "PE12 is a second data, reserved through solder bridge SB41 (OFF by default). PE12 is multiplexed with ARDUINO A2 pin." - [UM3300 Rev 1, section 8.5, p.24](https://www.st.com/resource/en/user_manual/um3300-discovery-kit-with-stm32n657x0-mcu-stmicroelectronics.pdf)
- The I/O assignment table lists PE2 as "CK" and PE8 as "D1"; a text search of the whole manual finds no occurrence of "SB19" and no other solder bridge tied to the microphone - [UM3300 Rev 1, I/O assignment table, p.33](https://www.st.com/resource/en/user_manual/um3300-discovery-kit-with-stm32n657x0-mcu-stmicroelectronics.pdf)
- Limitations: product DK32N6570$CR1 (MCU silicon revision "B", main board MB1939-N6570-C02) "No limitation"; MB1939 N6570-C02 "Initial revision", limitation "P9 of the STMod+ connector misses the SPI feature." - [UM3300 Rev 1, Tables 25 and 26, p.38](https://www.st.com/resource/en/user_manual/um3300-discovery-kit-with-stm32n657x0-mcu-stmicroelectronics.pdf)
- Schematic sheet 16 ("MEMs microphone", "Operation Voltage: VDD_MIC = 1.6 - 3.6V"): SB19 between VDD3V3 and VDD_MIC, drawn as a closed bridge; U14 `NX3L1T3157GMZ` with Z (pin 4) = PE8 / D1 (test point TP18), Y0 (pin 3) = Data_Con (TP19, to CN5 pin 6), Y1 (pin 1) = Data_Mems (TP20, from U13 DOUT), SEL (pin 6) = MIC_DET pulled to VDD_MIC through R105 10K, VCC (pin 5) = VDD_MIC with C119 100nF; CN5 pin 4 = PE2 CK, pin 5 = D2 (PE12), pin 10 = MIC_DET; note on the sheet: "Auto detect MIC board on connector. When MIC board plugged, bypass Data from on board MIC." SB41 on the PE12 / D2 net is marked DNF on the MCU I/O sheet - [MB1939 C-02 schematic, sheets 3 and 16](https://www.st.com/resource/en/schematic_pack/mb1939-n6570-c02-schematic.pdf)
- The VENC_RTSP_Server code confirms the PE12 second data line in software terms: "Mics 3&4 (REVB Only) => PE12 (SITF5)" with `AUDIO_MDF1_DATIN5_GPIO_PIN GPIO_PIN_12`, `GPIO_AF4_MDF1` - [VENC audio_multi.c L259-268](https://github.com/STMicroelectronics/STM32CubeN6/blob/main/Projects/STM32N6570-DK/Applications/VENC/VENC_RTSP_Server/Appli/Core/Src/stm32n6570_discovery_audio_multi.c)

### Inferences
- UM3300 calls the microphone data line "SAI_PDM", but every ST software package drives PE2/PE8 as MDF1_CCK0 / MDF1_SDI0 (AF4), and the manual's own block diagram lists MDF. The wording is loose; the SAI PDM function is not what ST software uses on this board.
- With no daughterboard, MIC_DET is pulled high by R105, so U14 connects PE8 to Y1 = Data_Mems (U13). A daughterboard presumably pulls CN5 pin 10 low to select Y0. A floating or contaminated CN5 pin 10 cannot pull the line low on its own, so the default routing to U13 is robust; TP18 (PE8), TP20 (U13 DOUT) and the clock at R104 are the natural probe points for a "noise only" investigation.
- U13 is powered from VDD_MIC = 3.3 V through SB19 with only 1 uF + 100 nF of local decoupling and no series filter; if SB19 were open the microphone would be unpowered and PE8 would float (noise only). SB19's default state is not stated in UM3300, only implied by the schematic symbol.

### Gaps
- The local UM3300 is Rev 1; a later revision (if any) could not be fetched from st.com, so later corrections to section 7.15.2 or the solder-bridge tables are unverified.
- UM3300 has no solder-bridge table entry for SB19, so its "default ON" state rests on the schematic drawing alone.
- The STEVAL-MIC008A's use of CN5 pin 10 (how it asserts detection) was not checked against that board's documentation.
