# Community reports: STM32N6570-DK onboard MEMS microphone (MP23DB01HP on MDF1)

Researched 2026-11-15. Sources: ST Community (fetched thread pages), GitHub (issues, PRs and source files read through `gh` and raw.githubusercontent.com), web search for Reddit / EEVblog / Hackster / YouTube / Edge Impulse / OpenMV / MicroPython.

Note on quotes: the page fetcher returned condensed posts, so quotes are short fragments (from the fetched page or from the search-engine snippet of the same page). GitHub quotes are verbatim from the API. Dates are as shown on the pages.

## Q1. Are there forum threads or issues about the STM32N6570-DK microphone giving noise, hiss, very low level or no audio? What was the resolution?

### Takeaway
Yes: at least three independent users on ST Community report exactly this symptom class on the STM32N6570-DK onboard microphone (noise only, or sound so faint that one has to blow into the microphone), on STM32CubeN6 v1.3.0 and v1.4.1, with ST's own MDF_AudioRecorder, BSP and GettingStarted-Audio code. None of these threads has a root cause or an accepted solution. The only positive "it records speech" report found for the onboard mic is a Zephyr PR (after a driver clamp bug fix).

### Cited Findings

**Thread A: "STM32N6570-DK mic and screen setup" (grashnar, Nov 20 and Dec 2, 2025). Board: STM32N6570-DK Rev B, STM32CubeN6 v1.3.0. No reply from anyone, no solution.**
- MDF_AudioRecorder: no audio on the headphone jack; "PcmBuffer (main.c) is always 0 filled" although the MDF half-complete and complete callbacks fire - [ST Community 159675](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mic-and-screen-setup-159675) (old URL: [td-p/858053](https://community.st.com/t5/stm32-mcus-embedded-software/stm32n6570-dk-mic-and-screen-setup/td-p/858053))

**Zephyr: positive report for the onboard mic.**
- Zephyr gained an MDF DMIC driver with STM32N6570-DK board support in PR #112277 (author rgallaispou, ST; merged 2026-09-03). Test method in the PR: dump the buffer with GDB and play it with `ffplay -f s16le -ar 16000 -ac 1` - [zephyr PR 112277](https://github.com/zephyrproject-rtos/zephyr/pull/112277)
- Follow-up fix PR #118736 (kartben, merged Sep 2026), verbatim: "`BIT()` has an unsigned type, so `-BIT(23)` is evaluated using unsigned arithmetic and wraps to a large positive value ... the bounds passed to `CLAMP()` are invalid." and "Heard on an STM32N6570-DK, whose microphone produced a full-scale square wave at pcm_width 24 and now records what is said to it." - [zephyr PR 118736](https://github.com/zephyrproject-rtos/zephyr/pull/118736)
- The Zephyr board file wires the onboard mic as: `&mdf1` kernel clock IC8 (`MDF1_SEL(3)`), filter `pdm0` at 0x52025080 with `mdf1_cck0_pe2` + `mdf1_sdi0_pe8`, `filter-order = <4>`, `st,reshape-filter-decimation = <4>`, `st,highpass-filter-cutoff = <0>`; the driver uses `MDF_SITF_NORMAL_SPI_MODE`, clock source CCK0, bitstream `MDF_BITSTREAMn_FALLING` - [stm32n6570_dk-common.dtsi](https://github.com/zephyrproject-rtos/zephyr/blob/main/boards/st/stm32n6570_dk/stm32n6570_dk-common.dtsi), [dmic_stm32_mdf.c](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/audio/dmic_stm32_mdf.c)
- Another tester on that PR (wouter-van-bastelaere-dekimo; STM32N6 but a DIFFERENT input, MDF1_SDI5 on PE12, external mic): (1) read timed out because the driver hard-coded `MDF_BITSTREAM0_FALLING` for every filter; fixed by deriving the bitstream from the filter index. (2) Audio that "sound[ed] quite bad" with "small silences and replayed segments" turned out to be his own rate assumption: "The MDF configuration could not generate exactly the requested 48kHz PCM rate with the available clock/divider ratios, so the actual rate was approx 47.xkhz." - [zephyr PR 112277 comment](https://github.com/zephyrproject-rtos/zephyr/pull/112277#issuecomment-5511459378)
- Zephyr's STM32 DMIC roadmap still lists for MDF: "Add DMA support", "Fix `DMIC_STATE_ERROR`", ADF support - [zephyr issue 108434](https://github.com/zephyrproject-rtos/zephyr/issues/108434)

### Inferences
- The symptom being debugged (noise only, essentially no acoustic response, ST example weak and hissy) is not unique to one board: grashnar (Rev B, FW 1.3.0) and velfinnix (FW 1.4.1) describe the same thing with ST's unmodified code paths, and neither got a resolution. That makes a pure "my firmware configuration is wrong" explanation less likely, and points at something common to these boards or to ST's reference settings. It does not prove a hardware fault: vedantgg and kartben got usable speech from the same microphone on the same board type.
- velfinnix's detail that tapping or blowing produces a faint response means the acoustic path was not fully dead on that board, only very insensitive. The case being debugged ("no response to tones or tapping") is a stricter failure than any forum report.
- vedantgg's "about 1 MHz PDM clock gives mostly silence at about -71 dBFS with bursts" is the one forum data point that looks like the debugged symptom, and there it was clock-frequency dependent (worked at about 2 MHz). In the debugged case the clock was swept 1.5 to 3.2 MHz without effect, so this does not explain it, but it shows the microphone/MDF pair does have a "runs, outputs noise floor only" mode.

## Q2. Does anyone report that the onboard microphone needs a very high digital gain (e.g. MDF gain 14-24), and that this is normal for this part?

### Takeaway
No forum post states this in words, but ST's own code shows it: the MDF_AudioRecorder example for this board sets `Gain = 14` (+42 dB) where the BSP uses `Gain = 2` (+6 dB) for the identical filter (Sinc4, R = 32, RSF /4), i.e. the example adds 12 steps (about 36 dB) on top of the CIC normalisation. Users running the BSP's normalisation-only gains are the ones reporting "very faint" audio.

### Cited Findings
- MDF_AudioRecorder (STM32CubeN6, STM32N6570-DK), exact settings in `main.c`: PLL3 from HSI (M 8, N 172, P1 7, P2 4, about 49.14 MHz), `ProcClockDivider = 2`, `OutputClock.Divider = 12` (CCK0 about 2.048 MHz), `MDF_SITF_NORMAL_SPI_MODE`, `MDF_BITSTREAM0_FALLING`, `MDF_ONE_FILTER_SINC4`, `DecimationRatio = 32`, **`Gain = 14`**, reshape filter enabled with `MDF_RSF_DECIMATION_RATIO_4`, HPF enabled with `MDF_HPF_CUTOFF_0_000625FPCM`, `DiscardSamples = 0`, 16 kHz out to SAI1 + WM8904 - [MDF_AudioRecorder main.c](https://github.com/STMicroelectronics/STM32CubeN6/blob/main/Projects/STM32N6570-DK/Examples/MDF/MDF_AudioRecorder/FSBL/Src/main.c)
- The example's README: "Digital microphone MP23DB01HPTR mounted on STM32N6570-DK board is used", kernel clock "around 49.152MHz using PLL3", processing clock 24.576 MHz, CCK0 2.048 MHz, "PCM samples at around 16KHz (2.048MHz/(32*4))", tested on "STM32N6570-DK (MB1939)" - [MDF_AudioRecorder README](https://github.com/STMicroelectronics/STM32CubeN6/blob/main/Projects/STM32N6570-DK/Examples/MDF/MDF_AudioRecorder/README.md)
- BSP (`stm32n6570_discovery_audio.c`) per-rate table, all Sinc4 with RSF /4, HPF 0.000625 fPCM, Offset 0, NORMAL_SPI, BITSTREAM0_FALLING, kernel clock IC8 from PLL3 (49.142 MHz; IC8 divider 1 for 8/16/32/48 kHz, 17 for 11/22/44 kHz, 7 for 96 kHz): decimation 64/64/32/32/16/16/16/8 and **gain -4/-6/2/2/10/10/10/18** for 8/11/16/22/32/44/48/96 kHz. So at 48 kHz ST uses Sinc4, R = 16, gain 10 (+30 dB) - [stm32n6570_discovery_audio.c](https://github.com/STMicroelectronics/stm32n6570-dk-bsp/blob/main/stm32n6570_discovery_audio.c)
- Zephyr's driver documents the scaling rule it applies (it always sets the largest non-saturating scale and ignores extra gain): "max scale = 20 * log10( 2 exp DS / D exp NF )", "DS = max data size at scale output (RSFLT on: DS = 22 / RSFLT off: DS = 24)"; and "The CIC output data resolution cannot exceed 26 bits", max decimation per order 0..5 = 512, 512, 512, 322, 76, 32 - [dmic_stm32_mdf.c](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/audio/dmic_stm32_mdf.c)
- User measurement on the DK: "Sinc5 at gain -8 gives the same loudness as Sinc4 at +2" (R = 32 in both) - [ST Community 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)
- velfinnix used the BSP_AUDIO functions (BSP gain table, no extra gain) and got "very faint" audio - [ST Community 167402](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6-nucleo-board-mdf-issue-mics-records-noise-167402)
- ST employee JonathanC: there is no official configuration; it "depends on the use case (near/far field, output bit depth, etc.)"; see X-CUBE-AUDIO-KIT and AN5795 - [ST Community 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)

### Inferences
- Applying the Zephyr formula (scale steps of about 3 dB, DS = 22 with the reshape filter): Sinc4/R32 normalises at +6 dB (gain 2), Sinc4/R16 at +30 dB (gain 10), Sinc5/R32 at -24 dB (gain -8), Sinc5/R16 at +6 dB (gain 2). These match the BSP table at 16 and 48 kHz and vedantgg's Sinc5(-8) = Sinc4(+2) observation. So the BSP gains are pure CIC normalisation (microphone full scale = PCM full scale), and the example's gain 14 is about +36 dB of real amplification.
- For the configuration being debugged (Sinc5, R = 16, RSF /4): the normalising gain is 2. A gain of 14 there would be about +36 dB above normalisation, equivalent to ST's example.
- With normalisation-only gain and a -41 dBFS/94 dB SPL sensitivity, conversational speech at the board lands around -65 to -75 dBFS, which on a 16-bit path is "very faint" but still clearly above the microphone's own noise. This plausibly explains the "faint, have to blow into it" reports made through the BSP. It does NOT explain "noise only, no response to tones or tapping": gain scales signal and microphone noise together.
- Worth checking in the debugged setup: at what gain setting is the -60 dBFS noise measured? Microphone self-noise (roughly -105 dBFS A-weighted from the datasheet SNR) plus about 36 to 42 dB of extra digital gain would by itself land near -63 to -69 dBFS. If the -60 dBFS figure is at normalisation gain, the noise is not microphone self-noise; if it is at gain 14 to 16 above normalisation, the noise level is about what a healthy microphone gives and only the missing acoustic response is abnormal.
- BSP values for 8 and 11 kHz (-4 and -6 with the same R = 64) do not follow the formula consistently, so the BSP table should not be treated as carefully derived.

### Gaps
- No ST statement found saying "gain 14 is required for this microphone" or explaining why the example and the BSP differ by 36 dB.
- No user reports a measured dBFS level for a known SPL on this board.
- The claim "works only up to gain 8" is for STM32U5 ADF and comes from a search snippet only (thread not fetched): [ST Community 133192](https://community.st.com/stm32-mcus-products-25/stm32u5xx-adf-as-pdm-mic-input-mono-and-dc-offset-133192).

## Q3. Any report of a hardware cause on this board (SB19 / VDD_MIC, analog switch U14 and MIC_DET, CN5, film over the sound port, bottom-port hole, board revisions, defective batches)?

### Takeaway
Nothing found. No forum post, GitHub issue or ST statement mentions SB19, VDD_MIC, U14 (NX3L1T3157), MIC_DET, a protective film, the sound port, a microphone change between board revisions, or a defective batch for the STM32N6570-DK.

### Cited Findings
- The only CN5-related thread: a STEVAL-MIC008A (dual MP23DB01HP) plugged into CN5 of the STM32N6570-DK. The poster states the onboard mic uses MDF instance 0 (PE8) with "Bitstream Matrix: Falling front" and "Interleaved mode: No". ST moderator Saket_Om (accepted answer): two microphones on one data line need two MDF filter instances; instance 0 with interleave set to 1, instance 1 without its own serial interface or output clock, same processing divider, taking the bitstream of serial interface 0 on the other edge; start instance 1 with `HAL_MDF_AcqStart_IT` and instance 0 with `HAL_MDF_AcqStart_DMA`. The thread says nothing about MIC_DET, U14 or whether the onboard mic is disconnected when CN5 is used - [ST Community 158093](https://community.st.com/stm32-mcus-embedded-software-32/interleave-audio-by-connecting-steval-mic008a-dual-mems-to-stm32n6570-dk-cn5-158093)
- The only board revision named by an affected user is "STM32N6570-DK, Rev B" (noise only, FW 1.3.0) - [ST Community 159675](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mic-and-screen-setup-159675)
- Hardware guesses made in the forum were generic and by a non-ST member: PCB noise coupling, the analogue jack / MICBIAS path being selected instead of the MEMS, "check that the mic's power and clock are enabled", and "It's very unlikely the MEMS is broken" - [ST Community 167402](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6-nucleo-board-mdf-issue-mics-records-noise-167402)
- ST employee Emmanuel_C notes that MP23 microphones are "Not Recommended for New Design" (a product status remark, not a fault report) - [ST Community 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)

### Inferences
- Because the STEVAL-MIC008A on CN5 shares the PE8 data line through the board's routing, a board whose data line is switched to an empty CN5 would give a floating or undriven input rather than a proper noise-shaped sigma-delta stream. The debugged board shows a proper noise-shaped stream at the pin, which argues the microphone is powered, clocked and connected; a blocked or damaged acoustic path (or a microphone whose membrane does not respond) would fit "valid modulator output, no acoustic response" better than a routing fault. This is reasoning, not a reported case.
- The absence of any "remove the sticker" or "wrong revision" report across roughly a year of forum traffic suggests there is no widely known hardware trap, but the sample is small (three affected users, zero follow-ups).

### Gaps
- No public errata or "known limitations" list for MB1939 covering the microphone was found; UM3300 and the schematic were not examined here (hardware documents are outside this task's community scope).
- No report compares MB1939 revisions (B vs C02) for the microphone circuit.
- Nobody reports probing VDD_MIC, the U14 select line or MIC_DET on a failing board.

## Q4. Any report that the microphone must be clocked or started in a particular way (continuous clock, wake-up time, mode switch)?

### Takeaway
Only two concrete data points: ST states the datasheet maximum wake-up time is 20 ms and recommends a 40 Hz HPF to shorten the start-up transient; and one user found the onboard mic gave "mostly silence (about -71 dBFS) with bursts" at a PDM clock of about 1 MHz while about 2 MHz worked. Nobody reports a required start sequence or a needed clock stop between modes.

### Cited Findings
- ST employee Emmanuel_C (Oct 13, 2026): per the datasheet the maximum wake-up time is 20 ms; the MDF HPF is first order and converges faster at higher cut-off; recommends 40 Hz instead of 10 Hz (10 Hz: 95 % in 48 ms, 99 % in 80 ms; 40 Hz: 95 % in 12 ms, 99 % in 20 ms) - [ST Community 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)
- User vedantgg on the DK: R = 16 with a PDM clock of about 1.024 MHz gave mostly silence at about -71 dBFS with bursts; the 2.048 and 2.08 MHz configurations worked; with the 10 Hz HPF there was a DC offset of about 0.04 FS and a start-up transient clipping for 0.5 s and decaying over about 4 s - [ST Community 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)
- ST employee JonathanC: `LF_MASTER_SPI` is only needed for low-power designs; it relaxes the processing-clock to sensor-clock ratio requirement (down to about 2x) - [ST Community 168802](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)
- All ST reference code for this board clocks the mic from MDF1_CCK0, enabled at MDF init and left running, NORMAL_SPI, sampling `BITSTREAM0_FALLING`: 2.048 MHz in the example, and (from decimation x 4 x rate) about 2.05 MHz at 16 kHz and about 3.07 MHz at 32/48 kHz in the BSP - [MDF_AudioRecorder main.c](https://github.com/STMicroelectronics/STM32CubeN6/blob/main/Projects/STM32N6570-DK/Examples/MDF/MDF_AudioRecorder/FSBL/Src/main.c), [stm32n6570_discovery_audio.c](https://github.com/STMicroelectronics/stm32n6570-dk-bsp/blob/main/stm32n6570_discovery_audio.c)
- Search-result snippet (ST product page / flyer, not fetched): the part has "power-down, low-power and performance mode" selected by clock frequency range - [st.com MP23DB01HP](https://www.st.com/en/mems-and-sensors/mp23db01hp.html)

### Inferences
- The 1 MHz result is consistent with the microphone entering its low-power mode (or sitting between mode bands) at that clock, where behaviour differs from performance mode. It is a user observation, not explained by ST in the thread.
- The debugged setup's findings (no dependence on edge, SPI mode, kernel clock, or PDM clock from 1.5 to 3.2 MHz) already cover every start/clock variable that the community has raised. No report suggests an additional sequence requirement.

### Gaps
