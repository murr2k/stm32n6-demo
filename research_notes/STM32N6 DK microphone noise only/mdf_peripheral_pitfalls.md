## Are there ST community threads, GitHub issues or errata where MDF/ADF output was noise-only or far too quiet, and what fixed it?

### Takeaway
Yes, and three of them are on this exact board and microphone (STM32N6570-DK, U13 = MP23DB01HP, MDF1 filter 0, PE2/PE8): users report "mostly noise", "very faint, I have to blow into it" and "random noise which changes every callback", and none of those threads has a confirmed root cause or fix. The one hard reference is ST's own example and BSP for this board, which use normal SPI mode, the FALLING bitstream, and (in the example) a SCALE of +42.1 dB, about 38.6 dB more than the reference manual's full-scale-safe value, because the on-board microphone's sensitivity is -41 dBFS, not the usual -26 dBFS.

### Inferences
- **The on-board microphone is 15 dB less sensitive than the "-26 dBFS" class that RM Table 290 and AN5795 implicitly assume, and ST compensates with digital gain in its HAL example.** Sinc4 with R = 32 has the same CIC gain as Sinc5 with R = 16 (32^4 = 16^5 = 2^20). RM Table 284 gives +3.5 dB as the maximum SCALE for that CIC gain with RSFLT; the ST example uses Gain 14 = SCALE 0x0E = +42.1 dB, that is 38.6 dB more. The ST BSP, in contrast, stays near the full-scale-safe value (Sinc4 R = 16 with +30.1 dB against a Table 284 maximum of 27.6 dB; Sinc4 R = 32 with +6 dB against 3.5 dB), which matches the "very faint" reports from BSP users in T1.
- Expected output levels, computed from RM gain formulas (CIC gain D^N, SCALE, RSFLT about +9.5 dB, 24-bit output) and the datasheet sensitivity, for Sinc5 R = 16 (or Sinc4 R = 32):
  - SCALE 0x01 (+3.5 dB): a full-scale PDM sine comes out at about -5 dBFS; 94 dB SPL at about -46 dBFS; speech at 65 dB SPL at about -75 dBFS; a 40 dB SPL room at about -100 dBFS; microphone self-noise at about -111 dBFS(A).
  - SCALE 0x0E (+42.1 dB, ST example): 94 dB SPL at about -7.5 dBFS; speech at 65 dB SPL at about -36 dBFS; a 40 dB SPL room at about -61 dBFS; self-noise at about -73 dBFS(A); clips above roughly 101 dB SPL.
- What the observed "-60 dBFS noise" can and cannot be, by level (assumptions as above):
  - A random or undriven-but-toggling data line (white 1-bit stream) would give about -20 dBFS with SCALE +3.5 dB (in-band fraction 21.3 kHz / 1.536 MHz = -18.6 dB of a full-power stream). That is 40 dB louder than observed.
  - A stuck data line (all 0 or all 1) or a strict 1010 pattern gives exact silence after the HPF settles, not -60 dBFS.
  - With SCALE near +3.5 dB, -60 dBFS is about 50 dB above the mic's self-noise and equals roughly 80 dB SPL of sound. With SCALE near +42 dB, -60 dBFS is exactly where a quiet room plus self-noise should sit. So the first thing to pin down is the SCALE value actually in `MDF_DFLT0CICR` during the capture: the same symptom is "impossible for a working mic" at one gain and "a working mic in a quiet room" at the other.
- T3's "mostly silence (about -71 dBFS) with loud bursts" at about 1 MHz matches the gap between the datasheet's low-power range (up to 1.1 MHz) and performance range (from 1.5 MHz): the microphone is not specified between 1.1 and 1.5 MHz. The 3.072 MHz used here is inside the performance range.
- T2's "noise that changes every callback" with all status codes OK is the same signature as the present case, on the same board, and was never resolved; so "no error flags, right rate, noise only" is a known unresolved community symptom for this board, with no evidence in those threads that the MDF silicon is at fault.
- LR is strapped high on U13 and ST selects `MDF_BITSTREAM0_FALLING` for it. This fixes the mapping for this board: LR = VDD goes with bs0_f (BSSEL = 00001).

### Gaps
- No thread gives a root cause for "noise only" on the N6570-DK on-board microphone. T1 and T2 are unresolved; T3 works but does not say what made it work beyond the configuration listed.
- I found no GitHub issue in STM32CubeN6, STM32CubeU5, stm32n6xx-hal-driver or stm32u5xx_hal_driver about MDF noise or gain (search engines only; the GitHub issue trackers were not queried directly).
- No Zephyr upstream DMIC driver for the STM32 MDF was found (only `st,stm32-dfsdm-dmic` exists in the docs index I searched), so there is no upstream Zephyr reference to compare against.
- The MP23DB01HP datasheet was not opened; its numbers above come from search snippets and one ST employee statement (wake-up 20 ms max).

## Is there any errata about the MDF bitstream matrix, the SITF sampling edge, or the CIC/SCALE path on STM32N6 or STM32U5?

### Takeaway
I could not open any errata sheet (st.com and st.com.cn dropped every fetch), so this question is only partly answered: search snippets show one MDF/ADF erratum family on STM32U5 and STM32H7Rx/7Sx (CCK1 not selectable for the SITF in LF_MASTER mode, which does not apply to a CCK0 design), and no snippet showed any MDF, ADF or GPDMA entry in ES0620 for the STM32N6. ### Cited Findings
- ES0499 (STM32U575/U585), per search snippets: MDF limitation titled "In LFM mode MDF_CCK1 clock cannot be selected for SITFx interfaces" (reported as section 2.12.1 in Rev 10, July 2024, and as 2.11.1 in another snippet), status "A" (workaround available), with a parallel ADF entry "ADF_CCK1 clock cannot be selected for the SITFx interfaces in LFM mode". ### Inferences
- The only MDF/ADF silicon erratum that surfaced (CCK1 in LF_MASTER mode) is irrelevant to a design that clocks the microphone and the SITF from CCK0. If the N6 shares it, the symptom would be confined to `SCKSRC = 01` in LF_MASTER mode.
- The SCALE "default value" inconsistency matters only to code that does not write `MDF_DFLTxCICR.SCALE`. The HAL always writes the whole register (HAL line 3377), so HAL users are unaffected; a hand-written driver should write SCALE explicitly and read it back.

### Gaps
- **ES0620 (STM32N6) was not read.** Whether it has an MDF, ADF, GPDMA or GPIO alternate-function section is unknown. This needs a manual download of the current revision (Rev 5 or later) and a check of the summary table. Same for ES0499, ES0553 (U59x/U5Ax), ES0595 (U5Fx/U5Gx), ES0596 (H7Rx/Sx) and ES0639 (H5Ex/5Fx): only snippets were seen.
- No erratum text was found about the bitstream matrix, the SITF sampling edge or the CIC/SCALE datapath on any family, but absence in search snippets is weak evidence.

## What exactly does RM0486 (STM32N6 reference manual) chapter on MDF say about the SITF clock constraints table, the SPI timing figure, and the recommended audio configurations table?

### Takeaway
RM0486 Rev 4 requires mdf_proc_ck > 2 x CCK in LF_MASTER SPI and > 4 x CCK in normal SPI, plus > 24 x CCK / (MCICD+1) when the reshape filter is on, and mdf_hclk >= mdf_proc_ck; the timing figure shows bsx_r sampled on the rising CCK edge and bsx_f on the falling edge; the 48 kHz recipe is row #11 (6.144 MHz kernel, PROCDIV+1 = 1, CCKDIV+1 = 2, Sinc5, decimation 16, SCALE 0x01 = +3.5 dB, RSFLT /4) and it only satisfies the clock rule in LF_MASTER mode. The manual states that CIC wrap-around is undetectable and that RSFLT overrun invalidates the samples.

### Cited Findings

Serial interface modes and clock constraints:

- "The LF_MASTER SPI mode is a special mode allowing the usage of a mdf_proc_ck clock frequency, only two times higher than the sensor clock. This mode is dedicated to low-power use-cases, using low-speed sensors." "In LF_MASTER SPI mode, the MDF must provide the bitstream clock to the external sensors via MDF_CCK0 and MDF_CCK1 pins". "For each SITFx, the application must select the same clock than the one provided to the external sensor (MDF_CCK0 or MDF_CCK1), in order to guarantee optimal timing performances." "Warning: The MDF_CKIx pin cannot be used in LF_MASTER SPI mode." - RM §35.4.3, p.1631-1632 (excerpt p.8-9)
- "The normal SPI interface is a more flexible interface than the LF_MASTER SPI, but the mdf_proc_ck frequency must be at least four times higher than the sensor clock." - RM §35.4.3, p.1632
- Clock source per mode: "If the serial interface is programmed in SPI mode, the selected clock source is a copy of the clock present on MDF_CCK0 or MDF_CCK1 or MDF_CKIx pin". "If the serial interface is programmed in LF_MASTER SPI mode, the selected clock source must be the clock directly provided by the CCKDIV to the MDF_CCK0 or MDF_CCK1 pin". - RM §35.4.3, p.1630
- Table 280 "Clock constraints with respect to the incoming stream" (rows as printed):
  - LF_MASTER SPI, "FMDF_CCKy max frequency limited to 5 MHz". RSFLT disabled: "Fmdf_proc_ck > 2 * FMDF_CCKy and Fmdf_hclk >= Fmdf_proc_ck". RSFLT enabled: "Fmdf_proc_ck > 24 * FMDF_CCKy / (MCICD+1) and Fmdf_proc_ck > 2 * FMDF_CCKy and Fmdf_hclk >= Fmdf_proc_ck".
  - MASTER SPI / SLAVE SPI (normal SPI), "FMDF_CKx max frequency limited to 25 MHz". RSFLT disabled: "Fmdf_proc_ck > 4 * FMDF_CKKy and Fmdf_hclk higher or equal to Fmdf_proc_ck". RSFLT enabled: "Fmdf_proc_ck > 24 * FMDF_CKKy / (MCICD+1) and Fmdf_proc_ck higher than 4 x FMDF_CKKy and Fmdf_hclk higher or equal to Fmdf_proc_ck".
  - Manchester, "FSYMB max frequency limited to 20 MHz": "Fmdf_proc_ck higher than 6 * FSYMB".
  - Footnote: "FMDF_CKKy represents the frequency of the clock received via MDF_CKIx and MDF_CCKy, or generated via MDF_CCKy." (The relation sign between Fmdf_hclk and Fmdf_proc_ck is lost in the text extraction for the LF_MASTER and Manchester rows; the SPI rows spell it "higher or equal".) - RM Table 280, p.1638 (excerpt p.15)
- Clock absence detection exists only in normal SPI mode: "The clock absence detection feature is not available in the LF_MASTER SPI mode." "When the serial interface is enabled, the CKABF flag remains to 1 until a first clock transition is detected." `STH[4:0]` "values lower than four are invalid". - RM §35.4.3 p.1632-1633, §35.8.3 p.1688

SPI timing (Figure 324) and the bitstream matrix:

- "For all SPI modes, the serial data is captured using the rising and the falling edge of the selected clock. The SITFx always provides the following bitstreams: bitstream received using the bitstream clock falling edge (bsx_f); bitstream received using the bitstream clock rising edge (bsx_r). According to the sensors connected, one of the two bitstreams may not be available." - RM §35.4.3, p.1632
- Figure 324 "SPI timing example" (read from the rendered page): the MDF_SDIx line carries L0 R0 L1 R1 ...; the sampling points are drawn at each rising edge of MDF_CCKy (taking the L value that was on the line before the edge) and at each falling edge (taking the R value); bsx_r then carries L0, L1, L2 and bsx_f carries R0, R1, R2, both updated on the bsx_ck strobe. - RM Figure 324, p.1632 (excerpt p.9)
- `BSSEL[4:0]`: "00000: bs0_r provided to DFLTx and SCDx; 00001: bs0_f provided to DFLTx and SCDx; 00010: bs1_r ... ; 00011: bs1_f ...". "If this bitfield selects a not instantiated input, the MDF selects the valid stream bsx_f having the higher index number." ### Inferences
- **Mapping of L/R strap to bitstream.** Figure 324 samples on the rising edge the value driven during the preceding clock-low half, and on the falling edge the value driven during the preceding clock-high half. A PDM microphone with LR low drives DOUT while the clock is low (data launched by the falling edge), one with LR high drives it while the clock is high. Hence LR = GND goes with bsx_r (`MDF_BITSTREAM0_RISING`, BSSEL = 0) and LR = VDD with bsx_f (`MDF_BITSTREAM0_FALLING`, BSSEL = 1). ST's choice of FALLING for U13 (LR pulled to VDD) agrees. For a single microphone on an otherwise undriven line, the "wrong" stream samples a floating line that usually still holds the previous bit, so both edges commonly give audio; the wrong edge alone is therefore unlikely to turn audio into pure noise.
- **Row #11 is an LF_MASTER-only recipe.** With mdf_proc_ck = 6.144 MHz and CCK = 3.072 MHz the ratio is exactly 2. Table 280 demands "> 2" for LF_MASTER (ST's own table uses exactly 2, so equality is evidently accepted) and "> 4" for normal SPI. Using row #11 clocks with `MDF_SITF_NORMAL_SPI_MODE` violates the manual; the manual does not say what happens (no flag is documented for it). For normal SPI at 3.072 MHz, mdf_proc_ck must exceed 12.288 MHz; ST's BSP uses 24.57 MHz (49.142 / 2) with CCK = proc / 8.
- **In normal SPI mode the SITF is clocked from the pad, in LF_MASTER mode from the internal divider** (text of §35.4.3 quoted above; Figure 323 draws the SPI-mode clock path coming back from the MDF_CCKy pad). So in LF_MASTER mode the filter produces samples at the right rate, with no flag, even if PE2 is not actually routed to MDF1_CCK0 (wrong alternate function, pin attribute, or a board fault) and the microphone gets no clock. In normal SPI mode a 48 kHz output proves that a clock is toggling at the PE2 input buffer. Since the symptom here is the same in both modes and the rate is right in normal SPI mode, the clock is reaching the PE2 pad; this argues against a missing or mis-muxed CCK0. It does not prove the clock reaches the microphone pin (R104) or that the data arrives through U14.
- For the context configuration (CCK 3.072 MHz, Sinc5, MCICD+1 = 16, RSFLT on), the constraints are: mdf_proc_ck > 4.608 MHz (RSFLT), > 6.144 MHz (LF_MASTER) or > 12.288 MHz (normal SPI), and mdf_hclk >= mdf_proc_ck. Sinc5 at 16 uses 21 of the 26 CIC bits, so CIC wrap-around is excluded. With SCALE <= +3.5 dB neither saturation nor RSFLT overflow is possible, and RFOVRF would flag an RSFLT overrun.
- None of the documented silent failure modes of the filter chain (CIC wrap, saturation, RSFLT overrun, FIFO overrun) produces low-level broadband noise: CIC wrap needs strong signals and gives gross distortion, saturation gives clipping and sets SATF, RSFLT overrun sets RFOVRF, FIFO overrun drops samples and sets DOVRF.
- The clock-absence flag CKABF is only meaningful in normal SPI mode. A driver that checks "no error flags" in LF_MASTER mode has no clock supervision at all.
- NBDIS tops out at 255 output samples (5.3 ms at 48 kHz), shorter than the microphone's 20 ms maximum wake-up time quoted by ST in T3 and far shorter than the HPF settling (48 to 80 ms at the 0.000625 setting). Start-up garbage must be discarded in software; this affects the first 100 ms only.

### Gaps
- The manual does not describe the behaviour when the SITF clock-ratio rule is violated, nor the duty cycle of CCK for odd CCKDIV+1 values.
- The exact sample point relative to mdf_proc_ck (how many proc_ck periods after the CCK edge the SDI pin is latched in LF_MASTER mode, and therefore the tolerated round-trip delay through R104, the microphone and U14) is not given in chapter 35. I did not check the N6 datasheet's MDF timing table.

## What does application note AN5795 (How to use the MDF to capture sound) recommend for gain/SCALE with real microphones, and does it describe symptoms of misconfiguration?

### Takeaway
AN5795 Rev 2 gives only full-scale-safe SCALE values derived from the 22-bit (RSFLT) or 24-bit rule; it never discusses microphone sensitivity, never recommends extra gain for a real microphone, and describes no misconfiguration symptoms. All its measurements were made on an STM32U5 with an emulated modulator, not a microphone.

### Cited Findings
- Applicable products: "STM32U5 series, STM32N6 series, STM32H5Ex/5Fx lines". "The ADF embeds the same chain filter as the MDF. All elements presented in this document are also applicable to the ADF". - AN5795 p.1, p.5
- Gain policy: "1. Check that the data size from the CIC filter does not exceed 26 bits ... For a PDM stream, the maximum peak-to-peak amplitude is equal of two (+/-1). If the peak-to-peak amplitude never exceeds 0.5, then SINpp can be one (+/-0.5). 2. Adjust the scale value in line with the RSFLT use by this formula: SCALEdB < 20 x log10(2^NB / (SINpp x R^N)) where NB is equal to 22 if the RSFLT is enabled, or 24 if the RSFLT is bypassed." "After the scale block, the signal is saturated at a maximum of 24 bits." - AN5795 §2.3, p.6
- "To maximize the efficiency of the RSFLT and to avoid a saturated output, the input size must be 22 bits." The scale block decreases "up to 8 bits (-48.2 dB), or increasing it up to 12 bits (90 dB) by 3 dB steps (+/-0.5 dB)" (the "90 dB" contradicts the RM's +72.2 dB). - AN5795 §2.3 p.5; contradicted by RM §35.4.8 p.1646
- "The RSFLT is highly recommended for audio application." "The HPF activation is highly recommended: ... The preamplifier and the microphone A/D converter induce a voltage offset (called DC offset)." "The implemented RSFLT has about 9.3 dB gain". - AN5795 p.6, p.13
- Recommended settings: Config 1 (512 kHz, no RSFLT): Sinc5/32 with 0x2B (-14.5 dB) or Sinc4/64 with 0x2F (-2.5 dB). Config 2 (512 kHz): Sinc5/8, 0x0C (36.1 dB), RSFLT. Config 3 (768 kHz): Sinc5/12, 0x06 (18.1 dB). Config 4: 2.048 MHz Sinc5/32 with 0x27 (-26.6 dB), or 1.024 MHz Sinc5/16 with 0x02 (6 dB); "A configuration using a decimation by 64 can also be used for 48 kHz audio. In this case, the input sample rate is 3.072 MHz, the SNR remains the same as well as the ripple, and the -3 dB cutoff frequency is 21.3 kHz." Measured SNR 119 dB (2.048 MHz) and 115 dB (1.024 MHz). - AN5795 Tables 3, 5, 7, 9, 10, p.15-23
- Measurement conditions: "Measurements have been performed on STM32U5 device, using a five-order sigma-delta modulator, with the microphone noise emulated by a noise shaper". "This noise shaper contains properly the noise in the useful band, for decimation ratios higher or equal to 64. For lower decimation ratio, the SNR in the useful band is degraded." - AN5795 §3.1, p.14
- Microphone modes: standby (no or very low clock), "low-power mode: sampling frequency between 350 kHz and 800 kHz", "normal or performance mode: sampling frequency from 1 MHz to 3.3 MHz". - AN5795 §3.1, p.14
- Clocking: "For an audio-capture application using digital microphones, the special mode LF_MASTER_SPI is highly recommended: in this mode, the mdf_proc_ck frequency can be only two times higher than the sensor clock." Table 13 repeats the LF_MASTER constraints (proc_ck > 2 x CCK; with RSFLT also > 24 x CCK / (MCICD+1); CCK max 5 MHz). "In some applications, the use of a PLL and an accurate reference generated from a crystal are needed". - AN5795 §3.4.1, p.25
- "Important: With these configurations [Config 1, no RSFLT], the rejection of frequencies between FPCM / 2 and FPCM is poor." This is the only place the note warns of a degraded result. - AN5795 p.16

### Inferences
- AN5795 and RM Table 290 size SCALE so that a 0 dBFS PDM signal just fits. For a microphone whose 94 dB SPL output is -41 dBFS (MP23DB01HP) that leaves ordinary sound 70 to 80 dB below digital full scale. Neither document warns about this; ST's HAL example for the board silently adds about 38 dB.
- AN5795 "highly recommends" LF_MASTER for microphones while ST's N6570-DK example and BSP use normal SPI and an ST employee (T3) calls LF_MASTER "unnecessary unless targeting a low-power use case". Both modes are evidently expected to work with a microphone; ST's shipped code for this board only exercises normal SPI.
- AN5795 Tables 15 and 16 list CCKDIV+1 values of 25, 13 and 12 although CCKDIV is a 4-bit field (maximum divide by 16 per RM §35.8.2). The table text is scrambled in extraction, so I may be misreading columns; treat as unverified.

### Gaps
- AN5795 contains no troubleshooting section and no statement of expected output level for a given SPL. The X-CUBE-AUDIO-KIT settings for the MP23DB01HP that an ST employee pointed to (T3) were not retrieved.

## How does the HAL convert the "Gain" parameter to the SCALE field, and are there known HAL bugs in stm32n6xx_hal_mdf.c / stm32u5xx_hal_mdf.c?

### Takeaway
`Gain` is not in dB: it is a signed step index from -16 to +24 (about 3 dB per step) written to SCALE as-is when non-negative and as `(Gain - 16) & 0x3F` when negative, which matches the reference manual's encoding. I found no published HAL bug for the MDF driver, but reading the source shows three behaviours that weaken "no error flags": in DMA mode the HAL never enables the RXFIFO overrun interrupt, its IRQ handler clears flags with a read-modify-write that wipes every pending flag, and it reports one flag per interrupt.

### Cited Findings
- Documentation in the source: "@param Gain Filter gain in step of around 3db (from -48db to 72dB). This parameter must be a number between Min_Data = -16 and Max_Data = 24." `#define IS_MDF_GAIN(PARAM) ((-16 <= (PARAM)) && ((PARAM) <= 24))`. - HAL source lines 1796-1797, header line 1054
- Conversion (identical in `MDF_AcqStart` and `HAL_MDF_SetGain`): `if (Gain < 0) { adjust_gain = Gain - 16; register_gain_value = ((uint32_t) adjust_gain & 0x3FU); } else { register_gain_value = (uint32_t) Gain; }` then `DFLTCICR = DataSource | CicMode | ((DecimationRatio - 1U) << MCICD_Pos) | (register_gain_value << SCALE_Pos)`. - HAL source lines 3363-3379 and 1817-1832
- `HAL_MDF_SetGain` and `HAL_MDF_GetGain` return `HAL_ERROR` unless the handle state is `HAL_MDF_STATE_ACQUISITION`. - HAL source lines 1808, 1856
- `MsbOnly`: `SrcAddress = (pDmaConfig->MsbOnly == ENABLE) ? (((uint32_t) &hmdf->Instance->DFLTDR) + 2U) : (uint32_t) &hmdf->Instance->DFLTDR;` In linked-list mode the HAL patches the head node: `LinkRegisters[NODE_CBR1_DEFAULT_OFFSET] = pDmaConfig->DataLength; ...CSAR... = SrcAddress; ...CDAR... = pDmaConfig->Address;` then `HAL_DMAEx_List_Start_IT`. The DMA data width is not checked against `MsbOnly`. - HAL source lines 1569-1579
- Interrupt enables in `HAL_MDF_AcqStart_DMA`: only `MDF_DFLTIER_RFOVRIE` (if the reshape filter is active) and `MDF_DFLTIER_SATIE`. `MDF_DFLTIER_DOVRIE` is enabled only in the interrupt-mode start (`DFLTIER |= (MDF_DFLTIER_DOVRIE | MDF_DFLTIER_FTHIE)`). - HAL source lines 1544-1551 versus 1367
- `HAL_MDF_IRQHandler` computes `interrupts = DFLTIER & DFLTISR`, handles flags in an `if / else if` chain, and clears with `hmdf->Instance->DFLTISR |= MDF_DFLTISR_DOVRF;` (same pattern for RFOVRF, SATF, CKABF). - HAL source lines 3009-3117
- `HAL_MDF_Init`: returns `HAL_ERROR` if the instance is already registered (`a_mdfHandle[...] != NULL`); programs the common clock generator (PROCDIV, CCKDIV, pins, trigger, then `CKGCR |= MDF_CKGCR_CKDEN`) only "for first MDF or ADF instance" (instance counter == 0), and returns `HAL_ERROR` if `CKGCR & MDF_CKGCR_CCKACTIVE` is already set. Output clock pins are written as `OutputClock.Pins | (OutputClock.Pins >> 4U)` with `MDF_OUTPUT_CLOCK_0 = MDF_CKGCR_CCK0DIR` (so DIR and EN are set together, before CKGDEN). `SITFCR = (Threshold << STH_Pos) | Mode | ClockSource` then `SITFEN`. - HAL source lines 314-449, header lines 430-456
- Clock absence API is refused outside normal SPI: `if ((hmdf->Instance->SITFCR & MDF_SITFCR_SITFMOD) != MDF_SITF_NORMAL_SPI_MODE)` returns an error. - HAL source lines 2186, 2248, 2303
- Kernel clock selection: `HAL_RCCEx_PeriphCLKConfig` for `RCC_PERIPHCLK_MDF1` with IC7 or IC8 does `MODIFY_REG(RCC->ICxCFGR, ICxSEL | ICxINT, ClockSelection | ((ClockDivider - 1U) << ICxINT_Pos)); LL_RCC_ICx_Enable();` then `__HAL_RCC_MDF1_CONFIG(...)`. - `stm32n6xx_hal_rcc_ex.c` lines 1333-1376
- Release notes of stm32n6xx-hal-driver, V1.0.0 (30-October-2024) through V1.4.0 (03-June-2026): a text search for "MDF" and "ADF" matched only the per-release module list, no change entry naming the MDF driver. - [stm32n6xx-hal-driver Release_Notes.html](https://github.com/STMicroelectronics/stm32n6xx-hal-driver/blob/main/Release_Notes.html)

### Inferences
- Gain to SCALE mapping check against RM Table 283: Gain 0 gives 0x00 (0 dB); 1 gives 0x01 (+3.5 dB); 2 gives +6.0 dB; 10 gives 0x0A (+30.1 dB); 14 gives 0x0E (+42.1 dB); 24 gives 0x18 (+72.2 dB); -1 gives 0x2F (-2.5 dB); -2 gives 0x2E (-6.0 dB); -8 gives 0x28 (-24.1 dB); -16 gives 0x20 (-48.2 dB). The sign handling is correct. The trap is the unit: passing a dB figure is silently accepted. "Gain = 3" meaning +3 dB yields +9.5 dB; "Gain = -12" meaning -12 dB yields 0x24 = -36.1 dB; "Gain = 6" yields +18.1 dB. Any value from 25 to 31 or below -16 is only caught by `assert_param`, which is compiled out by default; 25 to 31 would write reserved SCALE codes.
- **In DMA mode an RXFIFO overrun is invisible to a HAL user** unless the application reads `DFLTISR.DOVRF` itself, because DOVRIE is never set. "No error callback" therefore does not prove that no samples were dropped. Dropped samples give clicks and a rate deficit, not broadband noise, so this does not explain the present symptom, but the flag should be read directly.
- The `DFLTISR |= flag` idiom on a write-1-to-clear register writes back every flag that is currently set, so a SATF or RFOVRF pending at the same moment as the flag being serviced is cleared without being reported; the `else if` chain adds to that. A status check that relies on HAL error codes can under-report. Reading `DFLTISR` raw, before the HAL handler runs, is the reliable test.
- `MsbOnly` must agree with the DMA width chosen by the application: ENABLE with halfword transfers (ST example), DISABLE with word transfers (ST BSP). DISABLE with halfword transfers would deliver bits 15:0 of the data register, that is the low 8 bits of each 24-bit sample in the upper byte, which looks like loud noise. With 32-bit reads the sample is in bits 31:8; using it as Q31 or shifting right by 8 arithmetically is correct, while truncating the word to its low 16 bits gives noise. This is a classic way to get "noise at the right rate with no flags", but at a level near full scale rather than -60 dBFS unless further scaling is applied.
- `HAL_RCCEx_PeriphCLKConfig` side effect: selecting IC7 or IC8 for MDF1 rewrites that IC's source and divider. `SAI1SEL` and `ADF1SEL` offer the same ic7_ck / ic8_ck inputs (RM §14, RCC_CCIPR registers), so configuring the MDF clock through this call can change the clock of SAI1 (audio out) if both share the IC, and vice versa. ST's example keeps them apart (SAI1 on IC7 from PLL2, MDF1 on IC8 from PLL3).
- Changing PROCDIV or CCKDIV through the HAL requires de-initialising every filter handle of the instance first; a re-init of one handle while another is registered keeps the old clock dividers without error.

### Gaps
- No GitHub issue or release-note entry describing an MDF HAL defect was found for N6 or U5. The U5 HAL source and its release notes were not read; the N6 and U5 drivers are assumed, not verified, to share this code.
- I did not check whether Zephyr's STM32 clock-control or pinctrl code path for MDF1 on N6 differs from the HAL path (out of scope here; the application's own driver is the relevant code).

## Any reports about STM32N6 specifically: MDF clock source IC7/IC8 setup, missing sleep clock enables causing stalls, RIF configuration needed for MDF1?

### Takeaway
RM0486 documents that on the N6 a peripheral gets no kernel or bus clock while the CPU sleeps unless its PERxLPEN bit is set, and MDF1LPEN and GPDMA1LPEN reset to 0; ST's example does not appear to set them (it never sleeps). I found no community report tying missing sleep enables, IC7/IC8 setup or RIF attributes to MDF noise. ST's example makes the GPDMA channel secure and privileged with secure source and destination and marks PE2 and PE8 secure; a wrong attribute would stop data or clocks, not produce noise at the right rate.

### Cited Findings

### Inferences
- **Effect of WFI on the MDF if MDF1LPEN is 0:** the kernel clock stops in every idle period, so mdf_proc_ck and the CCK0 output stop with it. The microphone then sees a gapped clock. Samples stay bit-aligned (the MDF generates the clock it samples with), but the output rate falls below 48 kHz in proportion to idle time, and gaps long enough to take the clock below the microphone's 0.15 MHz power-down threshold put it to sleep, after which up to 20 ms of output is invalid. MDF Table 288's "Sleep: No effect" is only true with MDF1LPEN = 1. A capture that really delivers 48 000 samples per second of wall-clock time rules this out; a rate measured against the same gated clock would not. If GPDMA1LPEN alone were missing, samples would be lost to RXFIFO overrun (DOVRF), again a rate deficit.
- RIF or security mismatches are unlikely to produce the symptom: a non-secure or unprivileged DMA access to a secure resource reads zero or is ignored, a blocked RCC enable leaves the peripheral unclocked (and a register access then freezes the system), and a GPIO attribute problem stops the clock or data. None of these gives changing noise at the correct rate. That data arrives at all at 48 kHz shows the MDF1 clock enable, the kernel clock, the DMA request line and the DMA attributes are functional.
- IC7/IC8: a disabled IC (ICxEN = 0) or a wrong `MDF1SEL` gives no kernel clock, hence no samples, not noise. A wrong IC divider gives a wrong CCK frequency and sample rate. The relevant risk for audio quality is the choice of PLL reference: ST's example uses HSI, the BSP uses HSE; an HSI-derived clock is slightly off-frequency (T1) but does not create noise.

### Gaps
- No community thread or ST document was found that reports MDF misbehaviour caused by a missing `MDF1LPEN`, by IC7/IC8 configuration, or by RIF attributes. The sleep-clock mechanism above is derived from the RCC chapter and the project's own SAI/GPDMA experience, not from an MDF-specific report.
- No report was found of corrupted GPDMA linked-list nodes or of a required data-cache flush for MDF capture on Cortex-M55 or M7. The only data points: ST's example runs with D-cache enabled and no explicit cache maintenance in the lines I read, and the T1 user had caches disabled and still got noise. A stale-cache fault would show repeated or old buffer contents, not noise. I did not search the H7Rx/Sx or N6 GPDMA threads in depth ("GPDMA & HPDMA on STM32N6", "STM32N6 Nucleo audio input using SAI with GPDMA" appeared in results and were not opened).
- Whether the RIFSC RISUP for MDF1 must be set secure when the application runs secure was not established from the manual text I read; ST's example configures only the DMA channel and the two GPIO pins, not an MDF1 RISUP attribute.

## Summary catalogue: every way found for an MDF/ADF microphone capture to run without error flags and deliver wrong audio, and whether known MDF behaviour explains noise at about -60 dBFS

### Takeaway
Seventeen distinct mechanisms were found (list below). Only three fit "right rate, no flags, low-level noise, insensitive to edge, mode and clock ratio": the gain being 38 dB lower or higher than assumed for this microphone, a data path or sample-format problem outside the filter, and the microphone not delivering a valid stream (supply, clock range, wake-up, analogue switch). Nothing documented about the MDF silicon itself produces that signature, so the known evidence points away from the peripheral's filter chain and towards level expectations, the pin/board path, or post-processing.

### Cited Findings
Each item: symptom, cause, fix, source. Items marked (doc) are documented by ST, (field) are user reports, (code) follow from the HAL source.

1. Very low level with correct audio. Cause: SCALE sized for a full-scale PDM input per RM Table 284 / Table 290 while the MP23DB01HP delivers -41 dBFS at 94 dB SPL. Fix: raise SCALE (ST example uses Gain 14 = +42.1 dB with Sinc4/32) or apply gain in software. (doc + field) - RM Table 284 p.1649; [ST example](https://github.com/STMicroelectronics/STM32CubeN6/blob/main/Projects/STM32N6570-DK/Examples/MDF/MDF_AudioRecorder/FSBL/Src/main.c); [T1](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6-nucleo-board-mdf-issue-mics-records-noise-167402)
2. Wrong gain because `Gain` was given in dB. Cause: HAL unit is a step index. Fix: use the Table 283 code. (code) - HAL lines 1796-1797, 3363-3379
3. Saturation or rail values (0x7FFF). Cause: gain too high, HPF off with DC offset, or wrong GPIO configuration. Fix: enable HPF, lower gain, fix pins. SATF is set but only reported if the application looks. (field) - [T5](https://community.st.com/stm32-mcus-products-25/stm32u5xx-adf-as-pdm-mic-input-mono-and-dc-offset-133192), [T6](https://community.st.com/stm32-mcus-embedded-software-32/receiving-adf1-data-via-gpdma-161539)
4. Gross distortion on loud signals with no flag. Cause: CIC wrap-around above 26 bits (Sinc5 above decimation 32, Sinc4 above 76). "The MDF cannot detect or prevent a CIC wrap-around." Fix: respect Table 282. (doc) - RM p.1646
5. Invalid samples from the reshape filter. Cause: mdf_proc_ck < 24 x FRS. Flag RFOVRF is set; samples "are invalid". Fix: faster mdf_proc_ck. (doc) - RM p.1650
6. Mis-sampled bitstream. Cause: mdf_proc_ck not > 2 x CCK (LF_MASTER) or > 4 x CCK (normal SPI), or mdf_hclk < mdf_proc_ck. No flag documented. Fix: Table 280. Note RM row #11 is valid only in LF_MASTER. (doc) - RM Table 280 p.1638
7. Wrong channel or floating-line data. Cause: BSSEL selects the stream of the other clock edge (`MDF_BITSTREAM0_RISING` versus `_FALLING`); "one of the two bitstreams may not be available". Fix: LR = VDD uses bs0_f on this board (ST BSP). (doc) - RM p.1632; [ST BSP](https://github.com/STMicroelectronics/stm32n6570-dk-bsp/blob/main/stm32n6570_discovery_audio.c)
8. Samples at the right rate with no microphone clock. Cause: LF_MASTER mode clocks the SITF internally and has no clock-absence detection, so a CCK pin that is not really driven goes unnoticed. Fix: verify the pin with a scope, or use normal SPI where CKABF works. (doc, consequence inferred) - RM p.1630-1633
9. No clock on the pin although CCKxEN = 1. Cause: CCKxDIR = 0 ("must be avoided"), or CKGMOD = 1 waiting for a trigger, or dividers written while CKGACTIVE = 1 (write-protected, silently ignored). Fix: sequence of RM §35.4.5. (doc) - RM p.1636-1638, Table 287
10. Configuration writes silently ignored. Cause: SITF, BSMX, DFLT, CICR (except SCALE), RSFR fields are write-protected while the block's ACTIVE flag is 1; a new SCALE is ignored while the previous one is being applied. Fix: disable, wait for xxxACTIVE = 0, write, read back. (doc) - RM Table 287 p.1672, p.1646
11. Falling-edge filter does not start. Cause unknown (U5, TRGO-synchronised pairs). Workaround: init then de-init filter 0 first. (field) - [T4](https://community.st.com/t5/stm32-mcus-products/bsmx-falling-edge-data-not-always-available/td-p/688427)
12. Start-up thump and DC offset. Cause: microphone wake-up (20 ms max) plus HPF settling (48 to 80 ms at the lowest cut-off); NBDIS covers at most 255 samples. Fix: higher HPF cut-off (40 Hz recommended by ST), discard in software. (field, ST employee) - [T3](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802)
13. Near-silence with bursts. Cause: PDM clock about 1 MHz, between the microphone's low-power and performance ranges. Fix: clock inside 1.5 to 3.3 MHz. (field + datasheet snippet) - [T3](https://community.st.com/stm32-mcus-embedded-software-32/stm32n6570-dk-mp23db01hp-on-mdf1-recommended-cic-gain-hpf-pdm-clock-settings-for-16-khz-audio-and-start-up-thump-168802); [MP23DB01HP](https://www.st.com/en/mems-and-sensors/mp23db01hp.html)
14. Noise from sample-format handling. Cause: data register is 24 bits left-aligned in 32; `MsbOnly` reads from address + 2 and must match a halfword DMA; a mismatch or a truncation to the low 16 bits yields the sample's low byte. Fix: word DMA with `MsbOnly = DISABLE` and an arithmetic shift by 8, or halfword DMA with `MsbOnly = ENABLE`. (doc + code) - RM p.1666; HAL lines 1569-1570
15. Dropped samples without an error callback. Cause: HAL DMA mode does not enable DOVRIE; the handler's read-modify-write clear wipes other pending flags. Fix: read `DFLTISR` directly. (code) - HAL lines 1544-1551, 3009-3117
16. Rate deficit or stalls under an RTOS. Cause: `MDF1LPEN` / `GPDMA1LPEN` reset to 0, clocks stop in WFI. Fix: set the sleep enables. (doc for RCC; MDF effect inferred) - RM p.468-472, p.599-600
17. LF_MASTER with CCK1 as SITF clock does not work (U5, H7Rx/Sx errata). Workaround: select CCK0 for the SITF. (errata snippets) - [ES0499](https://www.st.com/resource/en/errata_sheet/es0499-stm32u575xx-and-stm32u585xx-device-errata-stmicroelectronics.pdf), [ES0596](https://www.st.com/resource/en/errata_sheet/es0596-stm32h7rxx7sxx-device-errata-stmicroelectronics.pdf)

### Inferences
- Against the context symptom (48 kHz, no flags, about -60 dBFS noise, unchanged by edge, mode, clock source and ratio):
  - Items 4, 5, 6, 9, 10, 16 and 17 are excluded or made unlikely by the configuration itself (Sinc5/16 is far from CIC wrap; the ratio and mode were varied; the rate is right) provided `DFLTISR` was read raw (item 15) and the rate was measured against an independent clock.
  - Item 7 alone should not remove all audio for a single microphone, and both edges were tried.
  - Item 8 is excluded if the normal SPI runs also produced 48 kHz, because that mode takes its clock from the pad.
  - Items 1, 2, 13 and 14 and the board path (U14 switch position via MIC_DET, VDD_MIC via SB19, R104) remain. The level arithmetic says a random or floating bitstream would be near -20 dBFS and a stuck line would be silent, so -60 dBFS is neither; it is either a real modulator stream seen through more gain than assumed (ambient noise in a quiet room is about -61 dBFS at ST's +42.1 dB) or a real stream damaged after the filter.
- A decisive, cheap discriminator that uses only documented MDF behaviour: set `HPFBYP = 1` and read the DC level. A live sigma-delta microphone shows a small stable DC offset (T3 saw about 0.04 of full scale at +6 dB; T5 saw about 1600/32768 at 0 dB on another microphone) that scales with SCALE in 3 dB steps; a stuck line shows plus or minus full scale; a floating line shows a drifting value. A second one: compare the raw `DFLT0DR` words with the DMA buffer contents to separate the peripheral from the transfer and format path.
- Replicating ST's exact example configuration (normal SPI, FALLING, Sinc4/32, Gain 14, 49.14 MHz kernel clock, PROCDIV+1 = 2, CCKDIV+1 = 12, about 2.05 MHz PDM clock, 16 kHz) is the closest thing to a known-good reference for U13, and at least one community user (T3) has the same topology working at about 2.08 MHz. No source was found that demonstrates the on-board microphone working at 3.072 MHz with Sinc5/16, although the BSP has a 48 kHz setting (Sinc4/16, CCK 3.07 MHz, Gain 10) and the datasheet range allows it.

### Gaps
- The errata sheets remain unread (see the errata section); a silicon limitation specific to MDF1 on the N657 cannot be excluded from snippets alone.
- No measurement or ST statement was found for the output level to expect from U13 with a given SCALE; the dBFS figures above are my calculation from RM formulas and datasheet snippets.
- Whether the 3.072 MHz PDM path on this board has timing margin in LF_MASTER mode (round trip through the microphone and U14 against an mdf_proc_ck of only 2 x CCK) is not documented anywhere I looked.
